# تطبيق عيادة المراعي البيطرية — النسخة المُصلَحة

لوحة الدكتور (`index.html`) + صفحة العملاء (`customer.html`) كتطبيقين PWA على GitHub Pages، مع Firebase (Auth + Firestore)، ومشروع Android (WebView) لبناء APK.

## هيكل المشروع
| الملف | الوظيفة |
|---|---|
| `index.html` | لوحة الدكتور (الواجهة والمنطق المحلي كما هو، مع إصلاحات) |
| `app-cloud.js` | تسجيل الدخول، المزامنة، النسخ الاحتياطي، طلبات العملاء، صفحة العملاء |
| `lib/sync-core.js` | محرك المزامنة (سجلات منفصلة، دمج ثلاثي، قائمة انتظار، صور منفصلة) |
| `lib/backup.js` | التحقق من النسخ الاحتياطية، التصدير/الاستيراد، ترحيل التصميم القديم |
| `customer.html` | صفحة العملاء (دخول مجهول Anonymous + ملكية الطلب) |
| `sw.js`, `manifest*.json` | PWA والعمل بدون إنترنت |
| `firestore.rules`, `storage.rules`, `firebase.json` | قواعد الأمان النهائية |
| `android/` + `.github/workflows/build-apk.yml` | مشروع Android وبناء APK (يدوي فقط) |
| `tests/` | اختبارات الوحدة، المتصفح، وقواعد Firestore (Emulator) |

## فكرة التصميم الجديد (باختصار)
- **الدكتور** = مستخدم Email/Password له مستند `admins/{UID}` في Firestore (يُنشأ يدويًا من الـ Console ولا يمكن كتابته من التطبيق). لا يوجد إيميل مكتوب في القواعد.
- **العميل** = مستخدم مجهول (Anonymous). يقدر فقط ينشئ طلبًا بحقول محددة، ويقرأ طلباته هو (`ownerUid == uid`). لا يقرأ طلبات غيره، ولا يكتب حالة أو ردًا.
- **البيانات**: كل سجل (مريض/موعد/مالية/كتاكيت/…) مستند منفصل بمعرّف ثابت ورقم نسخة `rev` وأوقات إنشاء/تعديل. القواعد تفرض `rev` يزيد 1 بالضبط، فلا يمكن الكتابة فوق تعديل أحدث بصمت.
- **الصور** الكبيرة تُحفظ في مجموعة `images` (وصور صفحة العملاء في `publicImages`) والسجل يحمل مرجعًا فقط. (Firebase Storage يحتاج خطة Blaze؛ ملف `storage.rules` جاهز لو رقّيت المشروع.)
- **التعارض**: دمج على مستوى الحقول (من غيّر حقلًا لوحده يكسب). لو الاثنين غيّروا نفس الحقل: الأحدث يكسب والقيمة الأخرى تُحفظ في «سجل التعارضات» (قابل للتصدير). الحذف مقابل التعديل: التعديل يكسب (لا فقد بيانات).
- **الأوفلاين**: التعديلات تُحفظ محليًا وتفضل «معلّقة» وتُرفع تلقائيًا عند عودة الاتصال بلا تكرار (معرّفات ثابتة + معاملات). الحالة تظهر دائمًا في الشريط العلوي: جارٍ الحفظ / تمت المزامنة / توجد تعديلات معلقة / لا يوجد اتصال / تعذر الحفظ. **المزامنة مع السحابة لا تعمل بدون إنترنت** — العمل المحلي فقط.
- **لا استبدال شامل صامت**: الاستيراد افتراضيه «دمج» (لا يحذف). «الاستبدال الكامل» يتطلب كتابة كلمة تأكيد، ويسبقه حفظ نسخة تلقائية، ويوجد زر «التراجع عن آخر استعادة».

## خطوات النشر (بالترتيب)

### 0) قبل أي شيء
1. من كل جهاز عليه بيانات: افتح التطبيق وصدّر **نسخة احتياطية** (الإعدادات ← تصدير نسخة احتياطية) واحتفظ بالملف.
2. لا تمسح بيانات المتصفح ولا تحذف التطبيق من الجهاز قبل اكتمال الترحيل.

### 1) إعدادات Firebase (يدوي — لا أستطيع تنفيذها نيابةً عنك)
1. **Authentication ← Sign-in method**: تأكد أن **Email/Password** مفعّل، وفعّل **Anonymous** (لازم لصفحة العملاء الجديدة).
2. **Authentication ← Users**: انسخ **UID** لحساب الدكتور.
3. **Firestore ← Start collection**: المجموعة `admins`، معرّف المستند = الـ UID الذي نسخته، وأضف أي حقل (مثلًا `ok: true`).
4. **Firestore ← Rules**: الصق محتوى `firestore.rules` ثم Publish (أو `firebase deploy --only firestore:rules`). إن ظهر خطأ صياغة في الـ Console أرسله لي.
5. (موصى به) **App Check** لتقليل الطلبات المزعجة من صفحة العملاء.

> ملاحظة: بمجرد نشر القواعد الجديدة، النسخ القديمة من التطبيق (أو APK قديم) لن تستطيع الكتابة في المستند القديم `clinic/data` (مقصود، حتى لا تتفرع البيانات). حدّث التطبيق على كل الأجهزة أولًا.

### 2) نشر الموقع
ارفع محتوى المشروع إلى المستودع (فرع GitHub Pages). ملف `sw.js` جديد الإصدار ويُحدّث الملفات القديمة تلقائيًا (Network-first)؛ افتح التطبيق مرة وهو متصل ثم أغلقه وافتحه ليتحدّث.

### 3) ترحيل البيانات القديمة
1. افتح لوحة الدكتور ← تبويب «العملاء» ← سجّل الدخول.
2. لو وُجد المستند القديم `clinic/data` تظهر رسالة ترحيل (مرة واحدة) تعرض عدد السجلات والتعارضات. وافق.
3. يُحفظ تلقائيًا نسخة احتياطية على الجهاز، ويُدمج المحلي مع القديم بالمعرّف (بدون حذف أي شيء)، ثم تُرفع السجلات كمستندات منفصلة، ويُكتب `meta/migration`.
4. المستند القديم **لا يُحذف**. بعد التأكد من سلامة البيانات على جهازين يمكنك حذفه يدويًا.
5. على الأجهزة الأخرى: سجّل الدخول فقط، والبيانات تنزل وتندمج.

### 4) اختبار صفحة العملاء
افتح `customer.html` من هاتف آخر، أرسل طلبًا، وتأكد أنه يظهر عندك، ثم ردّ عليه وتأكد أن الرد يظهر لنفس الهاتف فقط. (طلبات العملاء القديمة قبل التحديث ليس لها `ownerUid`، فيراها الدكتور لكن العميل القديم لن يرى ردها.)

### 5) بناء APK
- **Actions ← Build APK ← Run workflow** (يدوي فقط، لا يعمل تلقائيًا مع الـ push).
- `debug`: بدون أسرار، ينتج APK للتجربة كـ Artifact.
- `release`: أضف Secrets: `KEYSTORE_BASE64` (محتوى ملف keystore بصيغة base64) و`KEYSTORE_PASSWORD` و`KEY_ALIAS` و`KEY_PASSWORD`. لا تُنشر نسخة على Releases إلا إذا اخترت `publish`.
- التطبيق يفتح الموقع الحالي ويسمح فقط بنطاق `vetfarid.github.io/al-maraei-vet-app`. زر النسخ الاحتياطي يستخدم منتقي ملفات النظام داخل الـ APK.

## تشغيل الاختبارات
```
npm install            # مرة واحدة (يحتاج إنترنت)
npm test               # وحدة: المزامنة + النسخ الاحتياطي
npm run check          # فحص صياغة كل ملفات JS
npm run test:e2e       # المتصفح (Playwright + خادم Firebase وهمي)
npm run test:rules     # قواعد Firestore الحقيقية (Emulator)
```

## أمور يجب أن تعرفها
- التخزين المحلي (`localStorage`) **غير مشفّر**؛ لا تعتمد عليه كحماية للبيانات الحساسة، واستخدم قفل الجهاز.
- إعداد `ntfyTopic` في `firebase-config.js` يُرسل إشعارًا عامًا (بدون بيانات عميل) عبر ntfy.sh؛ اسم الموضوع معروف لكل من يرى الكود، فيمكن لأي شخص يعرفه إرسال إشعار مزيف. الحل الدائم Cloud Function (يحتاج خطة Blaze).
- الصور القديمة التي حُذفت من السجلات قد تبقى كمستندات يتيمة في `images` (لا تؤثر على العمل).
- حد التخزين المحلي للمتصفح نحو 5MB؛ الصور صارت تُضغط لنحو 380KB كحد أقصى للصورة، وإذا امتلأ التخزين تظهر رسالة واضحة بدل فشل صامت.
